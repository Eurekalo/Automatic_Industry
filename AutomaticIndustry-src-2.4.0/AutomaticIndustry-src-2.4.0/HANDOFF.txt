- Target framework: .NET Framework 4.7.2
- Patching        : Harmony 2 (Pardeike), PLib options (POptions), ILRepack merges
                    PLib into AutomaticIndustry.dll so the "Options" button shows.
- Repo layout     : src/ (C# sources), toolchain/Managed (game assemblies used for

                    toolchain/nuget, tools/ (name-extraction python helpers),

                    vanilla STRINGS where possible (VanillaBuildingNames.generated.cs).
- License         : MIT, original author credit: 一见倾心 (auto machine 机器自动工作).
- Design rules that MUST be preserved:
    * Never add new buildings; never change vanilla recipes/rates (except the
      explicit Oil Refinery 50%/100% option).
    * Every automation is an individual toggle; new automations default OFF.
    * All code comments in English, industrial-grade formatting.
    * Automation may only run when ALL vanilla run conditions hold (power,
      ingredients, cooldown, room, storage, environment).
    * No custom save fields beyond necessary [Serialize] timers.
    * Every patch wrapped in try/catch; a single failure disables one building,
      never crashes the game (see AutoWorkControllerBase circuit breaker).

--------------------------------------------------------------------------------
- ComplexFabricator family: duplicantOperated = false via prefab injection.
- Specialised controllers for: Oil Refinery (50/100 toggle), Oil Well Cap venting,
  GeoTuner, Food Smoker, Compost, Manual Generator, Telescopes, Mission Control,
  Tinker stations (Farm Station / Spice Grinder shell), Research buildings,
  Valves (liquid/gas value change without a Duplicant), Ranch stations
  (grooming / shearing / milking incl. Aquatic variants).

  vanilla "empty" workable/state transition) + HardThresholdRelease (hard 90%
  fill fallback for Desalinator salt, MilkSeparator Caviar/Brackwax).
- AutoEmptyTriggerPatches hooks MilkSeparator.RequiresEmptying and
  Desalinator.CreateEmptyChore for instant, vanilla-shaped drops.
- SweeperResearchDelivery option: research ManualDeliveryKG chores swapped from
  ResearchFetch to MachineFetch so Auto-Sweepers can supply Super Computer /
  Virtual Planetarium. NOTE: this is currently a BLANKET swap — see 2.1 below.
- Master switch "Enable all automation", bilingual option labels, live options
  language refresh (OptionsScreenRefresher), localization self-audit.

Known-broken / unsatisfying at 2.4.0 (reported by the user, all still open):
  a) Spice Grinder never actually seasons food automatically.
  b) Auto-Sweeper cannot move bottled water from LiquidBottler /
     LiquidPumpingStation into Advanced Research Center.
  c) Duplicants still walk up and "operate" machines that already run unattended,
     wasting Duplicant work time.
  d) Manual Radbolt Generator and Sushi Bar: incomplete loop animation, no
     progress bar.

2. VERSION 2.4.1 — PLANNED BUT **NOT IMPLEMENTED** (full analysis)
--------------------------------------------------------------------------------
Nothing below exists in the shipped 2.4.0 code. No file was modified for 2.4.1.

2.1 Spice Grinder真正的自动化 (issue a)
  Findings from IL:
    - Spice Grinder is NOT a plain ComplexFabricator. It owns
      `SpiceGrinder` / `SpiceGrinder.StatesInstance` plus `SpiceGrinderWorkable`.
      Setting duplicantOperated=false on a fabricator therefore does nothing.
    - Its food delivery chore is `CookFetch`, which robots (Auto-Sweeper) do not
      serve; the seasoned output is produced through the `SpiceFood` completion
      path inside the state machine.
  Plan:
    - New `AutoSpiceGrinderController : AutoWorkControllerBase` that drives the
      vanilla StatesInstance: only start when a valid spice recipe exists, spice
      ingredient present, a spiceable food target reserved, building operational,
      and no existing worker/reservation conflict.
    - Reuse vanilla target selection, storage reservation, work timer and the
      `SpiceFood` completion path. Cancel safely on target loss, power loss,
      disable, deconstruct, save/load. Never double-season, never double-drop.
    - Delivery: do NOT rewrite the global CookFetch chore type. Only for this
      building instance, add a robot-servable fetch path so both Duplicants and
      Auto-Sweepers can deliver ingredients/food.
    - Output must stay an ordinary ground `Pickupable` (no work-target binding)
      so vanilla Refrigerator / MiniFridge / SolidConduitInbox logistics take it.
      Do NOT write cross-building teleport code.

2.2 Advanced Research Center bottled-water supply (issue b)
  Findings:
    - Bottles emitted by LiquidBottler / LiquidPumpingStation carry
      `GameTags.LiquidSource`-style tagging that makes them non-pickupable for
      Auto-Sweepers in the relevant path.
    - 2.4.0's blanket ResearchFetch -> MachineFetch replacement is wrong: when no
      Auto-Sweeper exists or the sweeper cannot reach, Duplicant supply degrades.
  Plan:
    - Remove the blanket swap. Scope the change to the water `ManualDeliveryKG`
      of Advanced Research Center instances whose option is enabled; create an
      instance-scoped robot-compatible fetch path in ADDITION to the vanilla
      ResearchFetch so Duplicants keep working normally.
    - Never modify the global ResearchFetch / MachineFetch chore groups or
      Duplicant priorities.
    - For the bottler/pumping station only adjust pickupability of bottles that
      are ALREADY finished and released by vanilla. Never let the sweeper pull
      from inside building storage or substitute the bottling operation
      (avoids duplication, deletion, state-machine corruption).

2.3 Precise suppression of Duplicant "operate" chores (issue c)
  Plan:
    - Per automation mechanism, define which chores may survive: supply/fetch,
      pickup, empty, sweep = KEEP. Fabricate / Work / Research / Tinker =
      not created (or immediately cancelled) while that building's automation
      is enabled.
    - Prefer the building's native unmanned flag (duplicantOperated = false).
      Only for controllers without a native entry point do building-INSTANCE
      level chore suppression (LocalChoreProbe already finds the pending
      workable; extend it to cancel rather than only probe).
    - Never scan/modify global chore lists, never cancel logistics chores, never
      touch buildings whose automation is off; option hot-toggle must restore
      vanilla behaviour immediately.

2.4 Manual Radbolt Generator & Sushi Bar animation/progress (issue d)
  Plan:
    - Radbolt: run the vanilla fabricator order + work state instead of only
      playing a cosmetic anim. Sync `workTimeRemaining`, order progress,
      meter/progress bar, Operational active state and completion callback.
    - Sushi Bar: keep vanilla recipe queue and storage; while unmanned drive
      `working_pre -> working_loop -> working_pst` (verify actual kanim state
      names) and do NOT try to play Duplicant-only interaction anims.
    - Interrupt, power loss, order cancel, disable, deconstruct must stop the
      anim and reset progress; completion must fire exactly once.

2.5 Audit & verification checklist that 2.4.1 must satisfy
    - Per building: target selection, storage ownership, fetch type,
      reachability, worker dependency, animation, progress, completion,
      cancellation, save/load, deconstruct.
    - Test stubs: spice grinder with no target / vanished target / concurrent
      supply / duplicate tick; research water delivered by both Duplicant and
      Sweeper paths; automated work leaves logistics chores but no operate
      chores; Radbolt/Sushi interrupt-recovery and single completion.
    - Static audit: no global chore rewrites, no unsafe null-worker calls, no
      double release, no leaked event subscriptions, no per-frame logging.
    - Build Release with toolchain/Managed (U59), verify package structure,
      output AutomaticIndustry-2.4.1.zip + AutomaticIndustry-src-2.4.1.zip.
    - In-game stress scenarios cannot be replaced by stubs; ship an explicit
      in-game acceptance checklist.

--------------------------------------------------------------------------------
4. PRACTICAL NOTES FOR THE NEXT AI
--------------------------------------------------------------------------------
- Always resolve DLC-only types by NAME (TypeResolver-style / ConfigTypeName in
  AutomationRegistry). A missing type must be a silent skip, never an exception.
- Prefer vanilla state machines and vanilla completion paths over manual
  Storage.Drop; the hard-threshold code exists only as a last-resort fallback and
  historically caused item loss when used first.
- Reflection field/method names were verified against U59 assemblies in
  toolchain/Managed (excluded from the source zip for licensing reasons —
  re-copy them from OxygenNotIncluded_Data/Managed before building).
- Build: ./build.sh (dotnet build + ILRepack merge of PLib) -> dist/.
- Regression risks that bit us before: dropping input materials (Gleaner /
  Desalinator), Ice Kettle flooding the floor, shearing-station pathing loops,
  raw string keys shown in the options UI, and the mods screen losing the
  Options button when PLib was not merged.
